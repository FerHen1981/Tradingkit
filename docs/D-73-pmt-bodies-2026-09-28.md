# D-73 · Wat zit er in PMT's antwoord-body

**Meting: 28-09-2026 · 41 bestanden · 4539 PMT-rijen** — draaide op de VPS
tegen `/root/intent-store/routed_*.jsonl` via
`middleware/tools/analyze_pmt_bodies.py`.

Deze bevinding is de input voor **D-91** (T2, de bevestigingslaag). Zolang
onduidelijk was of PMT's body iets van broker-truth droeg, kon de laag niet
ontworpen worden. Nu is het duidelijk.

---

## Kernbevinding

**PMT's antwoord-body draagt géén fill-prijs, géén order-id, géén broker-truth.
Niet in 4539 rijen.**

De maximale informatie die PMT teruggeeft is: *"we hebben je POST ontvangen
zonder dat er iets misging aan onze kant."* Dat is een bevestiging van
ontvangst, niet van uitvoering. **T3 (fill) MOET dus uit een andere bron
komen (Fills-CSV / Rithmic).** Web's route-check van 07-09 klopt op de meting.

## Wat dit betekent voor D-91's T2-ontwerp

**T2 kan vier toestanden onderscheiden — niet meer dan dat.**

1. **`sent 200` + `{res:"Successfully send", error:false}`** — 90,4%.
   PMT accepteerde de order. Dit is de "verstuurd → geaccepteerd" promotie.
   Geen fill-info; alleen een ontvangstbevestiging.
2. **`sent 200` + lege body** — 9,1%. Zie *anomalie* hieronder. Vandaag
   behandelt de code dit als "sent" (want `Rejected()` retourneert false op
   een lege reply). Onduidelijk of dat correct is.
3. **`error 403`** — 0,5%. HTTP-level weigering vóórdat de order PMT
   inhoudelijk raakte. **Dit is broker-truth die we vandaag als "other" in de
   verdicts terugvinden.**
4. **`GEWEIGERD 200`** — 0%. De body-gebaseerde `Rejected()`-check in
   `Program.cs` heeft in 4539 rijen niets afgevangen. Dat is niet
   overbodig-omdat-het-niet-nodig-is, maar **omdat PMT `error:true` in de
   praktijk niet stuurt** — een echte broker-weigering komt als HTTP 403,
   niet als 200 + error-body.

## Anomalie — account …000205 draagt 100% van het niet-standaard verkeer

**Van de 414 lege bodies zit 100% op één account: APEX27002500000205.**
Van de 22 `error 403`-rijen zit 100% op **datzelfde account**. Dat is geen
statistische ruis — dat is een gerichte drift op één rekening.

Drie mogelijke verklaringen, en ze sluiten elkaar niet uit:

- **PMT-endpoint-configuratie voor dit account is anders.** Rithmic vs
  Tradovate zit vandaag op `MEX_PMT_RITHMIC_ACCOUNTS`. Account 205 zou daar
  in kunnen zitten — te controleren.
- **Auth/permissie-mismatch.** De 22 `error 403`-rijen wijzen op een
  autorisatie-fout op PMT-niveau, wat een setting-probleem is op dat account,
  niet een codewijziging.
- **Broker-side situatie op dit account** (bijv. account gepauzeerd,
  eval-limiet geraakt vóór PMT's boekhouding het wist). Dan zou PMT stil
  kunnen falen door een lege body terug te geven i.p.v. een fout.

**Aanbevolen actie**: één regel in `Program.cs` die logt welk endpoint werd
gekozen per POST (Rithmic vs Tradovate). Dan verdwijnt de eerste onbekende
vanzelf.

## Aanbevolen T2-poort (voor D-91)

Op basis van deze meting:

```
promote_to_confirmed(routed_row):
  match verdict, body:
    case "sent 2xx", {"error": False, ...}:  → CONFIRMED
    case "sent 2xx", <empty>:                → UNKNOWN  (flag account)
    case "sent 2xx", {"error": True, ...}:   → REJECTED  (praktisch onbestaand)
    case "error 4xx" | "GEWEIGERD ...":      → REJECTED
    case anything else:                       → UNKNOWN
```

De `UNKNOWN`-toestand is niet dood-materiaal — hij vangt de 9,1% lege bodies
en zichtbaar zijn is precies het punt van T2: **onbevestigd is een expliciete
toestand, geen poort die dichtvalt** (fase 2.2 van het herijkingsplan).

## Wat deze meting NIET beantwoordt

- **Sluit een `sent 200 + Successfully send` uit dat de broker later toch
  weigert?** Nee. PMT bevestigt ontvangst, niet uitvoering. Dat gat blijft
  bestaan tot T3 (Fills-CSV of Rithmic) draait.
- **Zit account 205 op Rithmic?** Eén `grep`-check op de env-var of één
  logregel per POST is het antwoord — nu niet gedaan.

## Reproduceren

```
python3 middleware/tools/analyze_pmt_bodies.py \
    --dir /root/intent-store \
    --samples 20
```

De analyzer trekt de body's uit het `result`-veld (opgeslagen door
`Program.cs::ForwardAsync` als `"sent <code> (poging <n>) · <body>"`,
tot 200 chars via `Excerpt()`). Grouped by shape, geclassificeerd op
sleutelwoorden (fill-info / confirm / error / unknown).
